Observações de fidelidade — o que está representado e o que não pôde ser comprovado

  • Origem real das chamadas à API: é o JavaScript do SPA React executando no navegador (axios.get/post/patch/delete em App.js). Não existe um serviço de front-end intermediando — o front-end é apenas arquivo estático servido pelo CloudFront.
  • DNS vs. tráfego: a resolução de app.* e api.* devolve um IP do edge da Cloudflare (registros CNAME "proxied"); o tráfego HTTPS posterior vai a esse edge, que decide para qual origem da AWS encaminhar. São coisas distintas e estão desenhadas com traços diferentes.
  • Cloudflare: a única regra configurada pelo grupo é a Transform Rule que injeta o X-Origin-Verify. Não há WAF customizado, rate limiting nem firewall rules próprias, e o "Always Use HTTPS" não está ativado — por isso o diagrama não afirma redirecionamento automático de HTTP para HTTPS.
  • Modo SSL/TLS "Full": a conexão Cloudflare→AWS é criptografada, mas nesse modo a Cloudflare não valida o certificado apresentado pela origem (validação estrita exigiria o modo "Full (strict)").
  • Ponto exato do bloqueio do back-end: quem devolve o 403 é o código do Lambda (index.js), não uma regra do API Gateway — o API Gateway aceita a requisição e a encaminha; a checagem do header acontece dentro da função.
  • Serviços gerenciados que reúnem etapas: API Gateway e DynamoDB geram e publicam suas métricas sozinhos — não há etapa de coleta separada, ao contrário do canário, que precisou de uma função nova porque não existe métrica nativa de "o domínio está no ar".
  • Limites de visibilidade (administrado pelo provedor): a topologia interna de execução do Lambda (sem VPC), o particionamento/replicação interna do DynamoDB e a forma como a AWS calcula os percentis de latência não são observáveis pelo grupo — por isso não estão desenhados como componentes.
  • Nada fictício: todos os recursos citados existem com os nomes/IDs mostrados (distribuição E107CAQRHXIBU9, API vfb3b537c6, funções sam-app-TodoFunction-ZBJ9ee0dV1L9 e sam-app-HealthCheckFunction-BlhQoK8Bfj8P, buckets todo-app-neshiku-frontend-1/2, tabela todos-table, dashboard todo-app-observabilidade) e estão definidos em backend/template.yaml. Cada um deles é conferido contra a AWS a cada execução de observabilidade_testes.py, que consulta os serviços e publica um inventário com os valores reais (distribuição, origens e origin group, ApiId e rotas, custom domain e target do CNAME, tabela e modo de cobrança, buckets com região e Block Public Access, regra de agendamento, retenção dos log groups e painéis do dashboard) na seção "Inventário do ambiente" de relatorio_testes_observabilidade.md — é assim que se verifica que este diagrama descreve o ambiente que está no ar, e não um desenho genérico.
  • Agendamento do canário: o SAM (Type: Schedule) cria uma regra do EventBridge (AWS::Events::Rule) — não o serviço "EventBridge Scheduler" (que seria ScheduleV2/AWS::Scheduler::Schedule). O diagrama e o caminho de console abaixo refletem o que de fato existe na conta.

Onde encontrar cada configuração (caminho no console de cada ferramenta)

Atalho que serve para quase tudo na AWS: Console AWS → CloudFormation → região Ohio (us-east-2) → Stacks → sam-app → aba Resources. Essa tela lista todos os recursos criados pelo template (Lambdas, API, tabela, log groups, metric filters, regra do EventBridge, dashboard) com link direto para o console de cada um.
Atenção à região no seletor do console: quase tudo está em us-east-2 (Ohio); o bucket secundário está em us-west-2 (Oregon); o certificado do CloudFront está em us-east-1 (N. Virginia) (exigência da AWS) e o CloudFront em si é global. Procurar na região errada faz o recurso simplesmente "não aparecer".

(em contas com o layout novo: Rules → Overview, e a regra aparece na lista com o tipo "Request Header Transform")		 A regra que injeta X-Origin-Verify nas requisições para api.neshiku.com.br. Front-end (CloudFront + S3)
Distribuição, domínio e certificado Console AWS → CloudFront (global) → Distributions → E107CAQRHXIBU9 → aba General → Settings Alternate domain name app.neshiku.com.br e o certificado ACM (us-east-1) que permite servir esse domínio
Redundância (Origin Group / failover) Mesma distribuição → aba Origins → seção Origin groups (e aba Behaviors → o comportamento padrão aponta para o grupo, não para um bucket) As duas origens S3, qual é a primária, e os "failover criteria" 403/404/500/502/503/504

Buckets e bloqueio público Console AWS → S3 → todo-app-neshiku-frontend-1 (us-east-2) e todo-app-neshiku-frontend-2 (us-west-2) → aba Permissions Block public access ligado e a Bucket policy que só autoriza o serviço do CloudFront com o ARN desta distribuição — são os dois controles que produzem o "BLOQUEADO" do diagrama
